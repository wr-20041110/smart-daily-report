# 智能日报生成器 · 项目提案（proposal.md）

| 项 | 内容 |
| --- | --- |
| 项目名称 | 智能日报生成器（Smart Daily Report Generator） |
| 版本 | v1（阶段一 · SDD 规范驱动） |
| 团队 | 王然（需求分析师）、咸哲（架构师）、王峻羽（开发工程师，兼任测试工程师与配置管理员） |
| 关联文档 | design.md、tasks.md、UML 附件（specs/uml/） |

## 1. 背景

团队成员的工作痕迹散落在 GitHub 提交、飞书任务、群聊消息等多个平台。下班写日报时普遍存在五个痛点：

1. **靠回忆**：下班回忆"今天干了什么"，全靠记忆翻找；
2. **多平台复制粘贴**：工作痕迹分散在多个平台，逐个查找粘贴；
3. **遗漏**：忙起来必有遗漏，写进去的都是"记得住的"，不是"做了的"；
4. **协作成果没人记**：你帮我改的接口、我们一起修的缺陷，经常谁都没写进日报；
5. **格式不一、汇总费力**：每人格式不同，组长手工汇总成团队日报。

本项目要正面解决这五个痛点：**让日报从成员的真实工作数据中"自动长出来"**——自动采集、自动归属、自动编排、自动推送，最小化手工编写，直至零手工。

## 2. 目标（可度量）

- **G1**：在配置齐全（或 mock 模式）下，执行一次日报流程（采集→生成→存储→推送），全流程耗时 ≤ 10 秒（本机、mock 数据规模 ≤ 200 条原始事件）。
- **G2**：日报条目覆盖团队全部 3 名成员，个人条目分类覆盖"开发 / 协作 / 讨论"三大类。
- **G3**：协同工作自动归属正确率 ≥ 95%（以 mock 数据集中 12 条协作事件为基准，归属结果与标注答案比对）。
- **G4**：日报生成与推送流程自动化率达到 100%——人工介入点仅剩：启动流程、配置成员清单（一次性）。
- **G5**：SQLite 留存全部历史日报与原始事件，支持按日期查询任意历史日报。
- **G6**：任一数据源不可用时降级出报（缺失源在日报中显式标注"无数据"），主流程不中断。
- **G7**：单元测试 + 集成测试全部通过，日报生成核心逻辑（归属规则、条目聚合、排版）语句覆盖率 ≥ 85%。

## 3. 范围

### 3.1 做什么（逐条编号，供用例追溯）

| 编号 | 功能条目 |
| --- | --- |
| F1 | GitHub 提交采集：读取团队仓库指定日期范围内的提交（作者、提交信息、变更文件、关联 Issue） |
| F2 | 飞书任务采集：读取任务流转记录（经办人、协作人、状态变更） |
| F3 | 飞书消息采集：读取团队群当日消息中 @成员 及与任务相关的讨论 |
| F4 | 个人日报生成：按成员聚合当日事件，生成"开发 / 协作 / 讨论"分类条目 |
| F5 | 协同归属：按三条规则自动归属协作成果（见 design.md 生成层） |
| F6 | 团队日报编排：将全组个人条目汇总为格式统一的团队日报 |
| F7 | 邮件推送：通过 SMTP 将团队日报发送给全体成员 |
| F8 | 飞书机器人推送：将团队日报推送到团队群 |
| F9 | 历史存储：SQLite 保存日报历史与原始事件（可追溯） |
| F10 | 主编排入口：CLI 一键执行"采集 → 生成 → 存储 → 推送"全流程 |
| F11 | Mock 数据源：无外部凭证时全流程可跑（测试、演示、开发期使用） |

### 3.2 不做什么（本期明确排除，逐条给理由）

| 编号 | 排除项 | 理由 |
| --- | --- | --- |
| X1 | 不做 AI 智能摘要（对日报内容做语义摘要润色） | 涉及 LLM 调用成本与幻觉风险，超出本期"自动化汇总"定位；列入 v1.1 候选 |
| X2 | 不做 Web 界面 | 本期以 CLI + 邮件/飞书推送交付，Web 端涉及前后端与鉴权，工作量与本期限定不符 |
| X3 | 不做考勤数据采集 | 考勤是独立数据源（第 4 周变更涟漪演练场景），本期聚焦提交/任务/消息三源 |
| X4 | 不做多团队多租户 | 本期为单团队假设，成员与仓库在配置文件中固定，多租户涉及隔离与权限设计 |
| X5 | 不自动写入飞书云文档 | 日报以消息与邮件形式推送 + 本地 SQLite 留存即可，云文档写入涉及额外授权范围与冲突处理 |

## 4. 技术约束

| 项 | 约束 |
| --- | --- |
| 语言 | Python 3.12+（开发环境实测 3.14.6 兼容） |
| 包管理 | uv（课程要求），requirements.txt 提供 pip 兜底 |
| 数据库 | SQLite（标准库 sqlite3，零部署） |
| HTTP 客户端 | httpx（见 design.md ADR-001） |
| 外部凭证 | GitHub Token（只读）、飞书应用凭证（app_id/app_secret）、SMTP 授权码——一律经本地环境变量注入，**严禁**写入代码或提交仓库 |
| 运行环境 | Windows 11 / macOS / Linux 均可，Python 3.12+ |
| 测试 | pytest；覆盖率统计 coverage |
| 代码规范 | PEP 8，ruff 静态扫描清零 |

## 5. 成功标准（验收核对表）

### 5.1 功能验收

| 编号 | 标准 | 度量方法 | 对应目标 |
| --- | --- | --- | --- |
| SC1 | 全流程一键可跑：单条 CLI 命令完成采集→生成→存储→推送 | 运行 `python -m daily_report_v1 --mock`，观察全流程输出与退出码 0 | G1 |
| SC2 | 三个采集源（GitHub / 飞书任务 / 飞书消息）各自可独立启用与降级 | 分别禁用任一源，验证日报生成仍成功且标注缺失源 | G6 |
| SC3 | 团队日报覆盖全部 3 名成员，条目含"开发/协作/讨论"分类 | 检查 mock 模式下生成的团队日报文本 | G2 |
| SC4 | 12 条标注协作事件归属正确率 ≥ 95%（≥ 11 条正确） | 运行集成测试 `test_attribution_accuracy`，比对标注答案 | G3 |
| SC5 | 日报历史可按日期查询 | 运行两次不同日期流程，SQL 查询两次历史 | G5 |
| SC6 | 邮件与飞书推送走通（真实凭证）或 mock 推送留痕（无凭证） | 检查推送结果记录与退出码 | G7 |

### 5.2 性能验收

| 编号 | 标准 | 度量方法 |
| --- | --- | --- |
| SC7 | mock 模式全流程 ≤ 10 秒（≤ 200 条原始事件） | 计时运行 |
| SC8 | 单数据源单轮采集请求数 ≤ 20 次 | 采集器内置请求计数断言（见 design.md 非功能约束） |

### 5.3 边界场景验收

| 编号 | 场景 | 期望行为 |
| --- | --- | --- |
| SC9 | 当日某成员无任何事件 | 该成员日报条目标注"今日无记录"，团队日报不缺失该成员 |
| SC10 | 凭证缺失（未配置环境变量） | 自动进入 mock 模式并在日报/日志中显式标注数据为模拟数据 |
| SC11 | 数据源返回异常（网络/限流） | 重试 3 次指数退避后降级出报，日志记录根因 |
| SC12 | 采集事件跨日（时区边界） | 按本地日期（Asia/Shanghai）过滤，事件时间以 UTC 存储、展示转本地 |

## 6. 术语定义

| 术语 | 定义 |
| --- | --- |
| 原始事件（RawEvent） | 采集层从各数据源拿到的统一格式记录：来源、类型、时间、作者、标题、URL、附加信息 |
| 日报条目（DailyReportEntry） | 生成层为一名成员一个分类产出的可读条目 |
| 团队日报（TeamReport） | 编排层汇总全部成员条目的最终日报文档 |
| 协同归属（Attribution） | 将协作成果（共同提交、协作任务、被 @ 的讨论）自动挂到相关成员名下的规则过程 |
| Mock 模式 | 凭证缺失或显式指定时使用内置模拟数据源运行，日报中显式标注 |
| 降级出报 | 某一数据源失败时跳过该源继续生成与推送，缺失源显式标注 |

## 7. 风险与预案

| 风险 | 影响 | 预案 |
| --- | --- | --- |
| 飞书应用审核未通过 | F2/F3/F8 无真实数据 | 先接 GitHub 数据源与 mock 数据，保证主流程可跑；凭证就绪后切换真实接口（接口契约已按"数据源可替换"设计） |
| GitHub API 限流（匿名 60 次/时） | F1 采集失败 | Token 只读授权、请求计数上限、指数退避重试（design.md 非功能约束） |
| 成员 GitHub 用户名与飞书 ID 不一致 | 归属错挂 | 配置文件维护成员名→各平台账号映射表，生成层按映射归并 |
