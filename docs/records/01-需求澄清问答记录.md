## 问答记录（节选 10 问）

| # | AI 提问 | 小组回答 |
| --- | --- | --- |
| Q1 | 日报的数据源有哪些？只接 GitHub 够不够？ | 三个：GitHub 提交、飞书任务流转、飞书群消息。GitHub 只覆盖代码工作，任务与讨论在飞书。 |
| Q2 | 谁看日报？组长、成员还是上级？ | 全员看：成员核对本人条目，组长审阅全组条目；邮件发给全员，飞书群推送一份。 |
| Q3 | 日报粒度多细？每条 commit 都写吗？ | 按"条目"聚合而非逐条 commit：同一成员同一分类合并为一条，内部按时间列出事件，避免刷屏。 |
| Q4 | 协作成果如何自动归属到人？ | 三条规则：commit 的 Co-authored-by、任务的协作人字段、群消息 @人且关联任务。归属错挂比漏挂更糟，规则必须可解释。 |
| Q5 | 缺勤（无任何工作痕迹）怎么处理？ | 不能静默跳过：该成员条目保留，标"今日无记录"。静默缺失会让读者以为漏了采集。 |
| Q6 | 时区怎么处理？GitHub 是 UTC，飞书是本地。 | 统一 UTC 存储、本地（Asia/Shanghai）展示，边界按本地日切。 |
| Q7 | 数据源挂了（限流/未审核）怎么办？ | 降级出报：缺失源显式标注"无数据"，其余源照常出报；日报宁可有标注的残缺，不可静默缺数据。 |
| Q8 | 凭证放哪？ | 一律环境变量注入，config.json 只放非敏感配置（成员映射、仓库名）。硬编码即红线。 |
| Q9 | 没申请到飞书凭证的时期怎么办？ | mock 数据源先行：内置模拟数据保证主流程可跑、可演示；凭证就绪后切换真实接口，接口契约按"数据源可替换"设计。 |
| Q10 | 日报历史要不要留？ | 要：SQLite 留存每日个人条目与团队日报全文 + 原始事件，支持按日期查询与追溯（哪条日报来自哪个提交）。 |

## 五大痛点 → 系统解法对照（proposal.md 背景）

| 痛点 | 系统解法 |
| --- | --- |
| ① 靠回忆 | 采集层自动拉取当日三源数据，无需回忆（F1–F3） |
| ② 多平台复制粘贴 | 统一 RawEvent 归一化格式，一次采集三源（F1–F3，design.md 3.1） |
| ③ 遗漏 | 数据驱动而非记忆驱动，事件 (source, ref) 唯一去重且可追溯（F9） |
| ④ 协作成果没人记 | 协同归属 R1/R2/R3 自动挂到相关成员（F5，design.md 5） |
| ⑤ 格式不一、手工汇总 | 统一模板编排 + 邮件/飞书自动推送（F6–F8） |
